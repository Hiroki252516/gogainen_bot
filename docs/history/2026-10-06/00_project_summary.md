# Project Summary

本リポジトリは、卒業研究用の「誤概念タイプと学習ログに基づくAI・情報系専門用語チューター」の仕様・実装リポジトリである。比較対象は、同じ知識資産を参照する通常AIチューター（control）と、学習ログに基づいて教授方略を変えるログ適応型AIチューター（proposed）である。

## Current MVP

新規実験の対象用語は次の3件に固定する。

| slug | 表示名 | RAG対象 |
| --- | --- | --- |
| `llm_knowledge` | LLMに知識を与える方法 | 第3章「LLMに知識を与える」 |
| `multi_agent` | マルチエージェント | 第4章「マルチエージェントとは」 |
| `memory_process` | 記憶プロセス | 第5章「記憶プロセス」 |

LangGraphは今回の対象用語・教材・RAG検索結果から除外する。過去のTransformer等のTerm、問題、ログはDB互換のため削除せず、新規seedでは非アクティブとして扱う。

pretest、retest、final_testの固定複数選択問題は、各問に正解3つ、M1誤答3つ、M3誤答3つ、J「わからない」を置く。現行実装ではテスト系と学習確認v1/v2のすべてでA〜Cが正解、D〜FがM1、G〜IがM3、Jがunknownであり、variant間の役割分散は行わない。正解ラベルを手掛かりにできるため、現行配置はデバッグ用であり研究データ収集には使用しない。採点は文字ラベルではなく提示問題の選択肢metadataを参照し、正解3つをすべて選んだ場合だけ正解、Jは単独選択だけ有効とする（学習確認v1は互換ルール）。不正解分類はM3、M1、知識不足の順に優先する。`l0_check`の自由回答と`transfer`の互換問題はこの10択ルールの対象外である。

**実験運用上の制約:** 現行コードの固定判定配置はデバッグ用である。実験開始前に判定位置を分散する実装・問題バンクへ変更し、全variantの分布をテストで検証するまで、参加者データを研究分析用に収集しない。現行コードに自動切替や実験用の別設定はない。

固定テスト問題と学習確認問題は `backend/app/seed/content/learning_content.yml`、新規参加者用の場面判断型学習確認問題v2は `backend/app/seed/content/learning_questions_v2.yml` を正本とする。新規参加者には作成時に学習確認v2を固定し、既存参加者および版未記録の既存行は学習確認v1を維持する。参加者向けのテスト表示は「テスト」「再テスト1」「再テスト2」とし、内部フェーズ `final_test` の表示も「再テスト1」に統一する。テストと再テスト1は各用語1問、再テスト周回は各用語5バリエーション（6回目以降は5問目を再利用）、学習セッションの確認問題は各段階・各用語5バリエーション（6回目以降は5問目を再利用）とする。

## Misconception taxonomy

| ラベル | 名称 | 本質 |
| --- | --- | --- |
| M1 | 誤信念型 | 単一の命題・信念が誤っており、その信念の修正が必要 |
| M2 | 欠陥メンタルモデル型 | 複数の信念がつながった説明モデル全体の再構成が必要 |
| M3 | カテゴリー誤り型 | 概念を誤った上位カテゴリーに分類しており、正しいカテゴリーへ再配置が必要 |
| M4 | 欠如したスキーマ型 | 必要なカテゴリーや関係に関する知識構造が不足しており、新しいスキーマの構築が必要 |
| unknown | 知識不足 | 「わからない」または判断に必要な知識が不足している状態 |

固定問題はM1/M3/unknownを診断対象とするが、AI内部taxonomyにはM1〜M4を保持する。内部ラベルは被験者画面に表示しない。

## Current implementation boundary

この章の「Current MVP」は、現在のコードとseedが実際に提供する範囲を示す。固定問題の採点、学習段階の遷移、評価値の計算はbackendが正本であり、AI出力は採点結果や遷移を上書きしない。

参加者の群割り当ては、管理者が実験運用時に決めたA/Bコードを被験者へ伝え、被験者が`/start`で入力する方式である。backendはAを`proposed`、Bを`control`へ変換し、`participants.assignment_method`には`admin_code`を保存する。被験者画面では群名や群の対応関係を表示せず、参加者が群を選択するUIも提供しない。

学習画面の`learning_stage`は、`enrichment`（豊富化）、`conceptual_change`（概念変化）、`final_feedback`（教材フィードバック）で表す。`L3`/`L2`は`scaffolding_level`に保存される内部互換・ログ値であり、参加者向けの段階名でも、L3からL2へ順番に進む独立した学習フェーズでもない。固定問題から直接判定された状態に応じて、backendが意味的な学習段階を決める。

- `retest` の採点APIは、1回の呼び出しで現在の再テスト回答を処理する。3用語の各1問が全件正解なら `survey` へ進み、それ以外は不正解・未回答用語を次の `learning_targets` に戻して最初の学習URLを返す。サーバーが自動的に学習・再テスト周回を繰り返すループや通知は未実装である。
- `l0_check` と `transfer` はYAML・DB互換の補助データとして残る。回答ログの `attempts.test_round` は初回を `test`、学習後の確認を `retest_1`、次周回を `retest_2` のように保存する。再テストの3用語が全問正解の場合はその満点を最終到達率に代用して追加の確認を省略し、不正解・未回答がある場合は学習セッションへ戻る。完全な転移評価や遅延再テストは将来対応である。
- 評価サマリーには現行のスコア、再発、負担、条件統制のJSONが保存される。一方、M2/M4固定問題の再発率、unknown継続率、転移率、足場掛け削減量など一部の値は現行実装で `null` または未算出である。

将来設計として、遅延再テスト、完全な転移評価、M2/M4を診断する固定問題、管理者による手動診断修正とその監査、詳細な群間グラフを追加できる。参加者削除と、ギブアップ・削除操作の監査記録は現行MVPに含まれるため、将来機能とは扱わない。

## Flow

1. 管理者から伝えられたA/Bコードを`/start`で入力し、`/consent`の仮同意書に同意する。参加者作成時にbackendがコードを内部群へ変換する。
2. 同意後に3用語についてテストを実施する。
3. 正解済み用語を除き、誤答・unknownの用語を学習対象にする。
4. 学習セッションでは共通RAGを参照してAIが教材本文を生成し、参加者に固定した版のYAML確認問題・選択肢をbackendが組み立てる。proposedだけが学習ログ、誤概念分類、足場掛け情報、過去応答を使う。問題文・選択肢は両群共通であり、参加者向けAPIに正答キーや選択肢ごとの採点・誤概念情報を含めない。
5. 再テストAPIで現在の回答を採点し、全問正解なら `survey` へ進む。不正解・未回答用語があれば `learning_targets` に戻り、最初の学習URLを返す。追加の学習・再テスト周回は現行UI/APIを研究者またはクライアントから再開する形であり、サーバーの自動反復ではない。
6. 再テストが満点でない参加者は、返された学習対象から次の周回を手動で再開する。初回テストで学習対象がない場合は、内部 `final_test` を参加者向けに「再テスト1」と表示し、全問正解なら仮アンケートへ、不正解・未回答なら `learning_targets` に戻す。アンケート送信後に `finish` を確定する。

controlにも同じRAG本文を渡すが、個人の履歴・誤概念taxonomy・教授方略情報は渡さない。
