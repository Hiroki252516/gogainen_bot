# 01. Research Requirements

## 研究目的

AI・情報系専門用語の学習において、学習者の回答履歴から誤概念タイプを推定し、説明方法と学習ステージを調整するAIチューターを設計・実装・評価する。

評価では、学習直後の正答だけでなく、同じ誤概念が再発しないか、足場掛けなしで自力解答できるか、別文脈で概念を使えるかを見る。

## 研究課題

### RQ1

誤概念タイプに応じて説明を変えると、同じ誤りの再発は減るか。

### RQ2

診断状態に応じて`enrichment`（豊富化）または`conceptual_change`（概念変化）の学習段階を調整する支援により、支援なし最終テストで解けるようになるか。

### RQ3

AI・情報系専門用語では、どの誤概念が再発しやすいか。

## 研究仮説

### H1

提案チューターは、通常チューターより同種誤答再発率が低い。

### H2

提案チューターは、通常チューターより足場掛けなし自力解答率が高い。

### H3

用語・誤概念タイプによって再発しやすさが異なる。

## 実験対象用語

現行実装の事前テストでは以下の3語を扱う。

| slug | label | 学習上の注意 |
|---|---|---|
| llm_knowledge | LLMに知識を与える方法 | 事前学習、ファインチューニング、プロンプト、RAGの役割を区別する |
| multi_agent | マルチエージェント | 複数エージェントの役割分担、協調、統合を区別する |
| memory_process | 記憶プロセス | 保存、検索、更新、利用の流れを区別する |

旧仕様・拡張候補:

- Transformer
- Loss
- ハルシネーション
- 正則化

旧用語と過去ログは削除せず、active seedと新規導線から除外する。

## 実験条件

### `group_condition = control`

通常AIチューター条件。

- 一般的な解説のみ
- 誤概念分類は分析用に内部保存してよい
- 誤概念分類を教授方略に使わない
- 学習ログ、誤概念タイプ、学習ステージに応じた個別化をしない
- 過去ログを参照した個別支援をしない
- 教材生成には用語情報と両群共通のRAGだけを使い、固定確認問題、選択肢、正答、参加者ID、群名はモデルへ渡さない
- 正答要約・誤答解説では、現在の問題、現在の選択、表示済み教材、共通RAGだけを使い、学習段階・診断・履歴・識別子を渡さない
- 一般的な誤解の説明や正確な訂正は妨げない。特定の学習者の誤答・診断に対応した説明は行わない
- チューター発話の `teaching_strategy` は原則 `general_explanation`

### `group_condition = proposed`

提案AIチューター条件。

- 誤概念タイプを教授方略に反映する
- `enrichment`（豊富化）または`conceptual_change`（概念変化）の学習段階で支援する。旧L3/L2は内部の`scaffolding_level`互換ログであり、参加者向けの別段階としては扱わない
- 再テスト結果で同種誤答再発を判定する
- 同種誤答再発を`recurrence_events`へ記録し、次回生成時の学習者状態・教授方略を再計算する。現行コードでは同じM1/M3に対して同じ`teaching_strategy`が再選択され、`TutorTurn.strategy_changed`は新規学習ターンで`false`として保存されるため、方略変更量の評価は将来対応である
- 過去の回答、誤概念履歴、現在の学習ステージ・足場掛け情報を支援生成に使う
- 固定確認問題・選択肢・正答は生成入力に含めず、表示・採点はYAML/backendが担う
- 教材生成では両群共通の用語情報と同一条件で取得したRAGを使う。個人IDと群名はモデル入力から除く

両群に同じ教材量の目標（本文700文字前後、許容範囲600〜850文字）を適用し、実生成の文字数・段落数・箇条書き数を記録する。許容範囲外の場合は、初回生成後に同じAI backendで最大2回再生成し、最大3試行とする。

## 実験デザイン

MVPでは参加者単位の群間比較を基本にする。

- 参加者を `control` または `proposed` に割り当てる
- 管理者が実験運用時にA/Bコードを決め、被験者へ伝える。被験者は`/start`でコードを入力する
- backendはAを`proposed`、Bを`control`へ変換する
- 割当方法は `participants.assignment_method=admin_code` として保存する
- 被験者画面では群名を表示せず、群を直接選択させない

このA/Bコードは現行MVPの運用上の割り当て手段であり、参加者本人を認証する招待トークンではない。管理者はコードを対象者へ個別に伝え、実験記録上の割り当てを管理する。過去ログ互換のランダム割り当て値や、参加者内で用語ごとに条件を変える設計は現行の参加者作成APIでは使用しない。

参加者数が少ない場合に備え、用語単位で条件を入れ替える被験者内比較も拡張可能にする。この場合は `term_assignments` に、参加者、用語、条件を保存する。ただしMVPでは参加者単位の条件を優先する。

## 問題タイプ

| 問題タイプ | 目的 | 使用フェーズ |
|---|---|---|
| `multi_select` | 固定選択肢で基礎理解を測る | pretest |
| `retest_multi_select` | 事前テストと同じ構成概念の再測定 | retest |
| `final_multi_select` | ヒントなしの最終測定 | final_test |
| `learning_multi_select` | 学習教材後の確認 | learning（提案群） |
| `control_learning_multi_select` | 共通教材後の確認 | learning（統制群） |
| `l0_free_response` / `transfer` | 互換・補助用の自由回答または転移 | 補助データ。主導線ではない |

事前テスト・再テスト・最終テスト・学習確認問題は、YAMLに固定した問題文と選択肢セットから出題する。再テストと学習確認はvariant_keyで再利用上限を管理する。

## MVPの成功条件

- 被験者IDを作成できる
- 事前テストを実施できる
- 事前テストは選択式回答のみを保存できる
- 誤概念分類を行える
- 事前テストで扱った3用語を出題できる
- 診断後、正解済み用語を学習対象から除外し、未達用語だけを学習対象にできる
- 再テストでは事前テスト対象の3用語を出題でき、v1〜v5と6回目以降のv5再利用を追跡できる
- 提案群ではM1〜M4/unknownの内部taxonomy、過去ログ、足場掛け情報に応じてAIチューターの支援が変わる。ただし現行の固定多選択問題が直接判定するのはM1/M3/unknownであり、M2/M4はAI内部taxonomyと将来の固定問題設計に保持する
- 学習ステージ、構成用語、回答十分性がログに保存される
- 再テストで同種誤答再発を判定できる
- 最終テストをヒントなしで実施できる
- 評価指標を管理画面またはCSVで確認できる

## 研究として壊してはいけない条件

- テストフェーズで答えやヒントを出さない
- 提案群と統制群の支援条件を混ぜない
- 被験者に内部分類ラベルを見せない
- RAG知識は両群で共通にし、提案群だけが学習者固有のログとtaxonomyを教授方略に使う
- LangGraphは対象用語、教材、RAG検索結果から除外する
- AI診断結果を管理者が上書きする手動修正UIと、その修正内容の監査ログ書き込みは将来対応である。参加者削除、学習・実験ギブアップの監査記録は現行MVPに含まれる。現行MVPではAI失敗をエラーとして記録し、手動修正済みとして自動確定しない
- 欠損、途中離脱、AI失敗を除外せず、分析時に判別できる形で保存する
