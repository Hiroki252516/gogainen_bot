## multi_agent / retest_v1

旅行会社が、公共交通を利用する日帰り観光プランを提案するAIシステムを開発している。

例えば、利用者が「午前に美術館、午後に水族館を訪れ、17時までに出発駅へ戻りたい」と希望した場合、観光候補の情報、訪問する順番や滞在時間、電車やバスの移動条件などを考慮して、実行可能な旅行計画を案内する必要がある。

開発担当者は、複数のAIエージェントに仕事を分担させ、協力して旅行計画を作成する仕組みを検討している。

このような旅行計画AIを実現するための開発担当者の対応として、適切なものを3つ選びなさい。

| 内部ラベル | 判定 | 選択肢 | 操作上の分類理由 |
| --- | --- | --- | --- |
| A | 正解 | 観光候補を調べるAI、訪問順や滞在時間を決めるAI、電車やバスの移動条件を確認するAIを設け、それぞれが何を調べ、何を判断するかを設定する。 | 役割別のエージェントと、担当ごとの情報収集・判断の範囲を設定する。 |
| B | 正解 | 観光候補担当が見つけた施設や営業時間を日程担当へ渡し、日程担当が作成した訪問順と予定時刻を移動確認担当に引き継ぐ仕組みを設ける。 | 前の担当の成果を次の担当の作業へ渡す経路を設計する。 |
| C | 正解 | 移動確認担当が、予定された出発時刻では17時までに駅へ戻れないと判断したら、その結果を日程担当へ返し、訪問順や滞在時間を見直せるようにする。 | 移動条件との矛盾を日程担当へ返し、担当間で計画を修正できるようにする。 |
| D | M1 | 観光調査・日程作成・移動確認のAIに役割を設定して個別に質問すれば、他の担当が出した結果も共有されると考え、調査内容を次の担当へ渡す仕組みは設けない。 | 役割名と個別の質問だけで情報共有も自動的に成立するとする誤り。 |
| E | M1 | 観光候補担当が選んだ施設について、日程担当が別の候補を求めると役割分担が崩れると考え、移動時間や営業時間が合わない場合も、担当間で候補の見直しを行う仕組みは設けない。 | 役割分担を理由に担当間で候補を見直せないと考え、条件に合わない候補へのフィードバックを設けない。 |
| F | M1 | 観光候補担当が営業時間に合う施設を選び、移動確認担当が利用できる電車を調べれば、各担当の結果を組み合わせるだけで17時までに出発駅へ戻れると考え、計画全体の時刻は確認しない。 | 各担当の部分的な条件が成立すれば全体の時刻も成立すると考え、17時までの帰着という計画全体の整合を確認しない。 |
| G | M3 | 1つのAIに「観光候補」「日程」「移動」の3つの見出しで回答させれば、各見出しが別のAIの担当に当たると考え、複数のエージェントが協力する構成として扱う。 | 一つの回答の見出しを、独立した担当エージェントと同じ種類として扱う。 |
| H | M3 | 電車の発着時刻だけを返す乗換検索ツールも、日程担当へ交通情報を渡す役割があるので、移動条件を判断するAIエージェントの一つとして数える。 | 時刻を返す検索機能を、移動条件を判断する担当エージェントとして数える。 |
| I | M3 | 1つのAIが移動距離に応じて徒歩と電車の案内を切り替える場合、切り替え先の処理をそれぞれ独立したAIエージェントとして数え、複数のAIが連携する構成とみなす。 | 一つのエージェント内の条件分岐を、独立した複数のエージェントとして数える。 |
| J | unknown | わからない。 | 特定の誤った主張を推測しない回答区分。 |

## memory_process / retest_v1

料理の献立を提案するAIサービスを開発している。ある利用者は以前の相談で「ピーマンは苦手なので、今後の献立には入れないでほしい」と伝えた。その後、別の日に「最近は食べられるようになったので、これからはピーマンも献立に入れてほしい」と希望を変更した。また、提案された料理について「味が濃かったので、次からは薄味にしてほしい」と感想を伝えた。開発担当者は、別の日に新しい相談が始まった場合にも、その利用者の新しい希望や過去の感想を適切に反映できる仕組みを作りたいと考えている。

この目的を実現するための情報の保存・利用方法として、適切な説明を3つ選びなさい。

| 内部ラベル | 判定 | 選択肢 | 操作上の分類理由 |
| --- | --- | --- | --- |
| A | 正解 | 利用者が「ピーマンを避けたい」と話した段階で、その希望を利用者別の記録に保存し、別の日の相談でも必要に応じて取り出し、献立の提案に利用できるようにする。 | 利用者別の希望を保存し、後日の相談で必要な記録を取り出して使う。 |
| B | 正解 | 本人が「今後はピーマンも使ってほしい」と希望を変更したら、以前の「避けたい」という記録を現在の希望と区別して更新し、その後の献立には変更後の条件を反映する。 | 以前の希望と現在の指定を区別し、有効な記録の扱いを更新する。 |
| C | 正解 | 料理への「味が濃かった」という感想から「次から薄味にしてほしい」という希望を記録し、後日の提案でも必要に応じて取り出して、味付けを考える際の参考にする。 | 感想から次回に役立つ希望を記録し、必要な場面で参照する。 |
| D | M1 | 過去の相談を全文保存しておけば、AIは別の日の相談でもそこに書かれた好みを自動的に把握できると考え、保存した会話から必要な情報を取り出す処理は設けない。 | 全文を保存するだけで次回の参照も自動的に成立するとする誤り。 |
| E | M1 | 利用者が「今後はピーマンも使ってほしい」と伝えたら、以前の「避けたい」という記録を残して新しい希望を追加し、どちらが現在の希望かを判断する仕組みがなくても、次回はAIが新しい方を使うと考える。 | 新旧の希望を保存するだけで現在有効な希望が自動的に選ばれると考え、変更・有効性を判断する仕組みを設けない。 |
| F | M1 | 「味が濃かった」という感想をもとにAIが一度薄味の献立を提案できれば、その改善内容は次の相談にも引き継がれると考え、感想や新しい希望を保存する処理は設けない。 | その場で改善できたことだけで、次回にも改善が保持されるとする誤り。 |
| G | M3 | 利用者が伝えた「ピーマンを避けたい」という希望を追加訓練でモデルの重みに覚えさせる処理を、利用者別の好みを保存し、必要に応じて更新・検索する記憶管理と同じ仕組みとして扱う。 | モデルの追加訓練を、利用者別の記録を保存・検索・更新する管理機構と同一視する。 |
| H | M3 | 以前AIが提案した「ピーマンを使わない献立」の履歴を保存し、その履歴を、利用者自身が伝えた現在の食材の希望を管理する記憶と同じものとして扱う。 | AIが生成した献立の履歴を、利用者本人が伝えた現在の食材希望を管理する記憶と同一視する。 |
| I | M3 | 同じ会話で「ピーマンも使ってほしい」と伝えた後の提案に希望が反映されたため、会話中の発言を参照する仕組みを、別の日の新しい会話でも好みを保存・更新する記憶機能と同じものとして扱う。 | 同じ会話の発言を参照する処理を、新しい会話をまたいで好みを保存・更新する記憶機能と同一視する。 |
| J | unknown | わからない。 | 特定の誤った主張を推測しない回答区分。 |

## 分類理由と解釈の範囲

マルチエージェントEは、役割分担が担当間の候補見直しを妨げると考える誤りを対象とする。Fは、各担当の部分的な条件が成立することから、計画全体でも帰着時刻の制約を満たすと判断する誤りを対象とする。役割を分けること自体や、結果を組み合わせること自体を誤りとはしない。

記憶Eは、古い記録と新しい希望を保存するだけで現在有効な希望を自動的に判断できるとする誤りを対象とする。更新のために古い履歴を必ず削除しなければならないという意味ではなく、履歴を残しながら現在の指定を管理する設計も認める。

記憶Hは、AIの生成した献立履歴と、利用者本人が伝えた現在の食材の希望を管理する記憶を同一視する点を対象とする。提案履歴を保存したり、補助情報として利用したりすること自体を否定しない。過去の提案内容だけから、本人の現在の希望を確定しない。

記憶Iは、同じ会話の発言を参照する処理と、別の日の新しい会話でも好みを保存・更新する記憶機能の混同を対象とする。会話内の参照や、保存した履歴を新しい入力へ渡すこと自体を一律に誤りとしない。

分類は本研究の操作的な割当であり、Chiの理論が個々の選択肢のM1/M3分類を直接実証したとは扱わない。機械検査・Mockの成功も、分類妥当性、初心者への読みやすさ、難易度同等性の実証ではない。研究者の内容確認・予備調査で別途確認する。
